# Proposed: a `gap` runtime event

Status: proposed, not applied. The contract is frozen and W3 did not change it.

## What happened

The runtime's event stream has no replay. When it drops, or when a run ends as
`interrupted`, some of the attempt's events were never received and the
transcript is incomplete. The adapter has to record that, because a transcript
with a silent hole reads as a complete one.

`RUNTIME_EVENT_TYPES` has six members and none of them says "history is
missing". `text_delta` comes closest, and the contract even documents an
ellipsis convention for it, but text deltas are explicitly non-durable
(`isDurableRuntimeEvent`), so a gap recorded there is a gap that vanishes.

## What W3 did instead

The gap is carried in the `attempt_outcome` event, inside the reason of a
`failed{retryable:true}`:

> the run ended as interrupted. Some events from this attempt were never
> received, so its transcript is incomplete.

That is durable, it reaches the transcript, and it is never a completion. It is
also prose, which means the UI cannot render it as anything other than a failure
message, and a reader has to parse English to learn that the hole exists.

## What would be better

A seventh event type:

```ts
z.object({
  ...runtimeEventBase,
  type: z.literal('gap'),
  reason: z.string(),
  /** Events between this and the previous durable event may be missing. */
  after_seq: z.number().int().nonnegative(),
})
```

It would let the client draw the hole where it happened rather than at the end,
and it would separate "this attempt failed" from "part of this attempt is
unknown", which are different facts that currently share one field.

Not urgent. The in-contract behaviour is correct; this is about how legible it
is to a reader. Worth doing before the transcript UI is built, since that is
what would have to render it.
