# Proposed - Contract additions for effect identity and trust-class admission

Status: proposed
Date: 2026-09-11
Raised by: the effect-identity lane, implementing note 0010

Every addition below is additive. Nothing frozen was removed, renamed, or
narrowed. `openapi.json` and `packages/client/src/schema.d.ts` were regenerated
with `bun run openapi` and `bun run client:generate`.

## New file: `packages/contracts/src/effects.ts`

The whole of the new vocabulary lives here rather than inside `broker.ts`, so the
frozen protocol file keeps its shape. It imports `proposeActionResponse` from
`broker.ts`; nothing in `broker.ts` imports back, so the direction stays acyclic.

| Export | What it is |
|---|---|
| `intentKey`, `intentKeyInput` | The identity of one intended effect: sha256 over the job, revision, connection, tool and payload hash, each part length-prefixed. |
| `sha256Hex` | The digest shape the file uses, matching the existing `payloadHash`. |
| `ORIGIN_TRUST_CLASSES`, `originTrust` | `owner`, `verified_connector`, `external_content`, `inferred`, `unknown`. |
| `TRUSTED_ORIGIN_CLASSES`, `isTrustedOrigin` | The two classes that carry an external write on their own. |
| `TRUST_GATED_EFFECT_CLASSES`, `isTrustGatedEffect` | `write_external` and `spend`. |
| `originField`, `originFieldCategory`, `originResolution` | A gated payload value, what it decides, and a resolver's answer for it. |
| `originWarning`, `originWarnings` | One doubt and a set of them, in plain words, for the approval screen. |
| `canonicalOriginWarnings`, `hashOriginWarnings`, `NO_ORIGIN_WARNINGS`, `warningsFor` | Stable ordering and the hash an approval is bound to. |
| `effectProposalResponse` | `proposeActionResponse` plus `intent_key`, `repeated`, `message`, `origin_warnings`. |

`effectProposalResponse` is an extension rather than an edit, so a caller that
parses with the frozen `proposeActionResponse` still succeeds and simply drops
the four new fields.

## Additive fields

| Schema | Field | Shape | Why |
|---|---|---|---|
| `entities.action` | `intent_key` | `sha256Hex.nullable().default(null)` | The effect's identity, so a re-proposal finds it. Nullable for rows written before the column existed; defaulted so an older producer still parses. |
| `entities.approval` | `origin_warnings` | `originWarnings.default([])` | The doubts the person was shown. A decision is bound to this set. |
| `api.approvalRequestWithOrigin` | `origin_warnings` | `originWarnings.default([])` | `approvalListResponse` now uses this extension of `approvalRequestView`, so the client can render "this address came from a web page fetched on Friday" instead of an address with no history. |

`approvalRequestView` itself is untouched; the extension lives in `api.ts`, which
already imports from both files.

## One edit inside the frozen `broker.ts`

`BROKER_ERROR_CODES` gains `'untrusted_recipient_origin'`. This is a widened
enum, not a changed or removed member. It is the only change to that file.

It matters that this is a code of its own rather than a reuse of
`approval_required`: the refusal is about where a value came from, and a UI or a
log that cannot tell the two apart cannot tell the person why they are being
asked again. Nothing switches exhaustively on `BrokerErrorCode`; the HTTP status
mapping in `apps/melete/src/broker/http.ts` falls through to 409, which is
correct for a refusal that a fresh approval resolves. `api.errorResponse.code` is
`z.string()`, so the OpenAPI document is unaffected by the widening.

## Schema

Migration `0010_effect_identity.sql`, generated by `drizzle-kit`:

```sql
ALTER TABLE "action" ADD COLUMN "intent_key" text;
ALTER TABLE "approval" ADD COLUMN "origin_warnings" jsonb DEFAULT '[]'::jsonb NOT NULL;
CREATE UNIQUE INDEX "action_intent_key_idx" ON "action" USING btree ("intent_key");
```

Postgres allows many nulls in a unique index, so existing rows are untouched
while every action created from now on is one effect exactly once.

**Note for the integrator:** the memory lane landed `0009_memory` while this work
was in flight, so this migration was regenerated as 0010 on top of it. If a third
lane also claims 0010, renumber this one and its snapshot and update the path in
`apps/melete/test/helpers/postgres.ts`, which now applies it alongside the frozen
initial schema so the unique index is actually exercised by the database tests.
